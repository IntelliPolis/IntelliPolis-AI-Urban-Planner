- **작업자:** 유서하

## 1. 작업 배경

### 1-1. 발견한 문제
`CityAnalysisService.create()`를 확인한 결과, Gemini AI 연동이 설계 의도대로 동작하지 않고 있었음.

- `AGENTS.md` 설계상 도시 분석은 **교통(TRAFFIC) / 환경(ENVIRONMENT) / 경제(ECONOMY) / 생활(LIVING)** 4개 도메인이 각각 다른 시스템 프롬프트를 가진 AI 에이전트로 분석되어야 함
- 그러나 기존 코드는 `UrbanAiService.explain()` 메서드 1개, 시스템 프롬프트 1개뿐이었고, `CityAnalysisService.create()`에서도 AI 응답 성공 시 **`agents.get(0)`(TRAFFIC) 하나만 덮어쓰는 구조**였음
- 결과적으로 AI가 성공하든 실패하든 ENVIRONMENT / ECONOMY / LIVING 3개 도메인은 **항상 규칙 기반(fallback) 문구만 반환**되고 있었음

### 1-2. 지켜야 할 제약 (AGENTS.md)
- AI는 점수(`score`)를 스스로 계산하거나 생성하지 않음 — 점수는 항상 규칙 기반 계산 로직(`CityScoreCalculator`)의 값을 사용
- AI는 입력에 없는 수치·예산을 임의로 만들어내지 않음
- AI 실패 시 규칙 기반 fallback으로 자연스럽게 대체되어야 함

→ 이 제약에 따라 오늘 작업 범위는 **"AI가 도메인별 `summary`(해석 텍스트)만 담당하고, `score`/`problems`/`suggestions`는 기존 규칙 기반 값을 유지"**하는 구조로 설계함.

## 2. 코드 변경 내용

### 2-1. `UrbanAiService.java` — 도메인별 에이전트 분리
- 기존: 시스템 프롬프트 1개, `explain(String json)` 메서드 1개
- 변경 후:
  - `analyzeDomain(AnalysisDomain domain, String json)` — 도메인(교통/환경/경제/생활)마다 다른 시스템 프롬프트로 Gemini 호출
  - `explainPlan(String json)` — 계획안 설명을 담당하는 최종 조정 에이전트 역할로 명확히 분리 (기존 `explain()` 역할 유지, 이름만 변경)
  - 공통 규칙(점수 임의 생성 금지, 입력 외 수치 생성 금지 등)을 베이스 프롬프트로 두고, 도메인별 관점(교통 혼잡/녹지 접근성/예산 효율/생활 인프라)을 추가로 주입하는 구조로 설계

### 2-2. `CityAnalysisService.java` — `create()` 메서드 수정
- 기존: `agents.get(0)`(TRAFFIC)만 AI 응답으로 덮어씀
- 변경 후: fallback으로 생성한 4개 도메인 각각에 대해 `ai.analyzeDomain()`을 호출
  - 도메인별로 성공/실패를 독립적으로 판단 → 일부 도메인만 AI 실패해도 해당 도메인만 fallback 유지, 나머지는 AI 결과 반영
  - 하나라도 실패한 도메인이 있으면 응답 최상위 `warnings`에 안내 문구 추가
- `explain(UUID id, PlanType type)` 메서드 내 `ai.explain(...)` 호출부를 `ai.explainPlan(...)`으로 변경 (이름 변경에 따른 후속 수정)

### 2-3. 버그 수정 — 도메인별 `warnings` 오표시
실제 API 호출 테스트 중 발견한 이슈:

- AI 호출이 **성공**한 도메인인데도 응답의 `agentAnalyses[i].warnings`에 `"AI 분석 대신 fallback 결과입니다."` 문구가 그대로 남아있는 것을 확인
- 원인: AI 성공 시 새 `AgentAnalysis` 객체를 만들면서 `summary`만 교체하고, `warnings` 필드는 fallback 객체의 값(`old.warnings()`)을 그대로 복사했기 때문
- 수정: AI 성공 분기에서 `warnings`를 빈 리스트(`List.of()`)로 설정하도록 변경
- 이 버그는 프론트엔드에서 "AI 분석 성공 여부"를 `warnings` 필드로 판단할 경우 잘못된 정보를 노출시킬 수 있는 문제였음

### 2-4. 계약 파일 변경 여부
`CityContracts.java`, `CityController.java`, `application.yml` — **변경 없음**. API 응답 구조(`AgentAnalysis` 레코드 등)는 기존 그대로 사용.

검증 항목:

3. **warnings 초기화 검증**: AI 성공 시 해당 도메인의 `warnings`가 비어 있는지 확인 (버그 수정 후 추가한 회귀 테스트)

## 4. 실제 환경 검증 (mock이 아닌 실제 Gemini 응답)

로컬 환경변수(`SPRING_AI_MODEL_CHAT=google-genai`, `GEMINI_API_KEY`)를 설정한 뒤 `bootRun`으로 서버를 직접 띄워 실제 API 호출 검증 진행.

**검증 대상**: `POST /api/city-analyses` (부산광역시 가상 해안구 샘플 데이터)

### 확인된 결과
- 4개 도메인(`TRAFFIC`, `ENVIRONMENT`, `ECONOMY`, `LIVING`) `summary`가 모두 실제 입력 데이터(혼잡 도로명, 공원 면적 비율, 고령 인구 비율, 예산 등)를 반영해 서로 다른 내용으로 생성됨을 확인
- `score`는 AI 응답과 무관하게 규칙 기반 계산값 그대로 유지됨을 확인 (AI가 점수를 임의 생성하지 않는 제약 준수)
- 버그 수정 후 재검증: 성공한 도메인의 `warnings`가 정확히 `[]`로 반환됨을 확인
- `plans` 3종(균형형/환경 중심형/예산 효율형)과 도메인별 `expectedScores`가 정상 반환됨을 확인
- 최상위 응답의 `warnings`가 빈 배열로, 4개 도메인 모두 AI 분석에 성공했음을 확인

### 트러블슈팅 기록
- 환경변수에 `GOOGLE_API_KEY`와 `GEMINI_API_KEY`가 동시에 설정되어 있을 경우, Spring AI가 `GOOGLE_API_KEY`를 우선 사용한다는 경고 로그(`WARN ... Using GOOGLE_API_KEY`)를 확인 — 향후 유사 이슈 발생 시 참고할 수 있도록 기록

## 7. 발견 및 공유 사항 (팀 논의 필요)

- **[해결 완료]** AI 성공 시에도 도메인별 `warnings`에 fallback 문구가 남아있던 버그 — 수정 및 회귀 테스트 추가 완료
- **[정보 공유]** `backend/data/raw`(원본 CSV)는 `.gitignore` 대상이라 각자 로컬에 파일이 없으면 `UrbanDataServiceTest`가 실패함 — 신규 합류자나 환경 재설정 시 유의 필요
- **[정보 공유]** 로컬에서 Gemini 실제 연동 테스트 시, `application.yml`을 직접 수정하지 않고 로컬 환경변수(`SPRING_AI_MODEL_CHAT`, `GEMINI_API_KEY`)로만 오버라이드하는 방식을 사용 — 공용 설정 파일 변경 없이 개인 환경에서만 AI 경로를 켤 수 있음
